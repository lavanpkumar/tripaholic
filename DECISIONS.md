# Decisions

One line per decision or deviation from PLAN.md. Newest blockers first.

## Blockers
- **No `MONGODB_URI` / `GEMINI_API_KEY` in the dev environment yet.** `npm run smoke:mongo` and `npm run smoke:gemini` print "... is not set" and exit with code 1 until they are added to `.env.local`, so the Phase 0 acceptance test still needs a run with real keys. The app itself runs on the local file store meanwhile.
- **Vultr + GoDaddy Registry need the team's accounts.** Planned for Phase 6: deploy files in `deploy/` and a README "Deploy" section; the server, DNS, and HTTPS steps themselves need someone with those accounts.
- **Grok Bot PR access not verified.** Claude Code cannot test Grok Bot. Branches are pushed with a `HANDOFF.md`; whoever opens PRs (Grok Bot or a human with `gh pr create`) should use it.

## Scope
- Sentient OS integration dropped (team decision, 2026-11-14: it is only a sponsor). The booking agent (Phase 4) will be native Gemini function calling behind `runAgent(ctx, request, emit)`.

## Phase 0
- Next.js 16.4 App Router + React 19 + Tailwind v4; Node runtime only.
- shadcn/ui not used: the repo already had a finished visual design (initial commit), so components are small hand-built Tailwind pieces in that design's palette (pine green accent, Inter). Avoids the default-template look.
- MongoDB via the official `mongodb` driver (no Mongoose). Documents use a string UUID as `_id`; the app sees it as `id`.
- Local fallback store: when `MONGODB_URI` is empty, the same repository API reads/writes `.data/db.json`. Lets the app and demo run before Atlas is wired up.
- Planned for Phase 3 (planner) and Phase 4 (agent): an offline fallback for AI. When `GEMINI_API_KEY` is empty or Gemini fails, a deterministic planner and agent produce results and the UI labels them "offline", so the demo never dead-ends on an API failure. Phase 0 only reports whether Gemini is configured.
- Gemini model comes from `GEMINI_MODEL`; `lib/env.ts` has a fallback only so a missing var does not crash the server. Confirm the current fast model at https://ai.google.dev/gemini-api/docs/models when adding the key.
- Event times are floating local ISO strings (`2027-02-08T09:00:00`, no offset) in the destination's wall-clock time. The calendar runs in UTC mode so these display unchanged; booked flights (Phase 4) will be converted from origin to destination time.
- Trip status is derived using "today" in the destination's time zone.
- Dynamic server pages call `await connection()` (Next 16 guidance) instead of `export const dynamic`.
- `AGENTS.md` is generated by `next dev`; committed as the file itself recommends.
- Single demo user (`demo-user`), no auth, per PLAN.md Section 3.
- Branch protection on `main` was not set up by Claude Code (the tool permission was declined); set it in GitHub settings.
- Phase branches are stacked (`cc/phase-1-*` branches from `cc/phase-0-*`, and so on) because earlier phases are not merged yet; merge PRs in phase order.
- Gemini errors are typed (`GeminiError.kind`: auth, rate_limit, timeout, server, grounding_unsupported, bad_request, invalid_output). 429/5xx get bounded backoff (2 retries, 1 s then 2 s); auth, timeouts, and other 400s are thrown at once. Search grounding is dropped only when Gemini says the tool is unsupported for the request, and that fallback is logged. (PR #1 review.)
- The file store sorts like Mongo (numbers numerically, before strings) so local and Atlas ordering agree. (PR #1 review.)

## Phase 1
- Place lookup uses Open-Meteo geocoding (free, no key, returns IANA time zones). It does not index states/provinces, so `lib/geo.ts` adds a built-in list; if the geocoder is unreachable, built-in cities are used. Unknown free text is accepted with the browser's time zone.
- `destination.name` stores the resolved label ("Tokyo, Japan") rather than the raw typed text, so prompts and cards are unambiguous.
- Trip length capped at 30 days to keep planner prompts and the calendar readable.
- New trips open on the Flights tab, matching the demo flow (flights, lodging, then itinerary).
- Accepted on purpose (PR #2 review): `lib/geo.ts` lands whole in Phase 1 (one gazetteer for place search, the mock flight provider, and the offline planner), and `lib/validation.ts` holds the Phase 3/4 input schemas too, so all API inputs live in one file. Splitting them across the stacked branches would only add merge churn.

## Phase 2
- Events are stored in floating destination time; the calendar shows the whole trip (up to 7 days, then weekly paging) plus a Day view.
- Shrinking trip dates is rejected with a 409 naming how many events would fall outside, instead of deleting or clipping them silently (PR #3 review).
- Booking events can be renamed and annotated, but their times only change through the booking; the API compares against stored times, so forms that resend unchanged times work (PR #3 review).

## Phase 3
- Planner output includes 2-3 `highlights` (title + body) beside the free-text `summary`, so the "Why this plan" panel matches the original design.
- Post-processing drops (rather than truncates) events outside the trip or flight window, and shifts AI events forward past conflicts within the same day; anything that no longer fits before 23:00 is dropped. Buffers: 90 min after landing, 150 min before departure.
- Gemini failures never block the itinerary: the offline planner runs and the summary carries a notice naming the cause (`GeminiError.kind`).
- The "Ask AI to adjust this plan" box regenerates with the request as `preferences` (no chat thread).
- The file store reloads `.data/db.json` when its mtime changes, so `npm run seed` and the dev server can share it.
- AI events the traveler moves or edits are pinned (`pinned: true`, set automatically by PATCH): Regenerate keeps them and plans around them. They can be unpinned from the event card. (PR #4 review.)
- Generate holds an in-process lock per trip (409 while running) and inserts the new plan before deleting the old one. The lock is per Node process, which matches the single-instance Vultr deploy. (PR #4 review.)
- The 4-hour cap on shifting AI events lives in Phase 3's post-processing (it was first added on the Phase 4 branch). (PR #5 review.)

## Phase 4
- Provider `book()` takes the full option rather than only its id, so a stateless provider can book exactly what was shown; the agent resolves ids against options it has seen in the same run.
- Each agent run gets only the two tools for its kind (`search_flights` + `book_flight`, or `search_lodging` + `book_lodging`), so a flight request can never book a hotel.
- Airlines and properties are fictional names; photos reuse the design's three sample images. Everything is labeled demo data.
- "Arrive before noon" means on the trip's first day. For long-haul routes the agent also searches the day before, so travelers land on day one.
- Flight blocks on the calendar show the 2 h before landing and the first 2 h of the return flight, not the whole flight. Hotel check-in/out are moved around flights (landing + 90 min, airport − 150 min).
- Multiple bookings per trip are allowed; each can be cancelled from its tab (`DELETE /api/bookings/:id`), which also removes its calendar blocks.
- SSE over a POST `fetch` (not `EventSource`, which cannot POST). If the browser disconnects, the run still finishes and its log is saved; the tab shows the latest run on reload.
- Each option the agent sees is stored with the query that produced it, so bookings use that search's dates, guests, and passengers (prices always match). Model-supplied dates are checked (YYYY-MM-DD, within the trip, allowing a day early for flights/check-in) and errors go back to the model as tool errors. (PR #5 review.)
- `POST /bookings/confirm` takes a per-run lock and re-reads the run inside it, so a double-click or retry books exactly once (409 for the other). (PR #5 review.)

## Phase 5
- The Phase 5 acceptance test ("run the demo flow three times without errors") is automated as `npm run demo:check -- <baseUrl> --runs 3`, so it can be rerun on the Vultr deployment and with a Gemini key. Result in this environment (offline mode): PASS, 3 runs, ~9 s each.
- After a booking lands on top of an existing AI plan, the itinerary offers a one-click replan instead of moving AI events automatically, so nothing changes without the user asking.

## Phase 6
- Deploy target: one Vultr Cloud Compute VM (Ubuntu 24.04) running the Next.js **standalone** server under systemd (no PM2), behind Caddy for automatic HTTPS. Single instance, which the in-process generate/confirm locks rely on.
- Caddy does not compress the agent's SSE route and flushes immediately (`flush_interval -1`), so steps stream live.
- Secrets live only in `/opt/tripaholic/.env` (mode 600, read by systemd); scripts read it through an `.env.local` symlink. Nothing secret is committed or shown by `/api/health`.
- Claude Code could not create the VM, register the domain, or connect Atlas/Gemini (no account access). Those steps are scripted and listed in `docs/SUBMISSION.md`.
- Deploys don't wait for keys (PR #7 request): `setup.sh` treats a missing or failing Gemini key as a warning (offline mode) and a missing `MONGODB_URI` as a warning (file store), but a set-and-broken `MONGODB_URI` stays fatal. `--strict` makes both fallbacks fatal for the final pre-submission deploy.
- The file store honors `DATA_DIR`; on the server it is `/opt/tripaholic/data`, because `next build` wipes `.next/` (where `cwd/.data` would otherwise live under the standalone server).
- `.env.example` keeps comments on their own lines, since systemd's `EnvironmentFile` doesn't strip inline `# ...`. (PR #7 review.)

## Phase 7 (stretch)
- Sentient OS wrapper: dropped (see Scope). Search grounding: available since Phase 3 via `GEMINI_GROUNDING=true`.
- Real flight sandbox adapter: not built (needs provider credentials). `PROVIDER_MODE=real` logs a warning and uses mock data.
- `.ics` export (`GET /api/trips/:id/itinerary/ics`): events use `TZID=<destination zone>` with a generated `VTIMEZONE` (RFC 5545 §3.2.19). Its observances are derived from the zone's real offsets via `Intl` for the trip's years ±1, so DST is right and Outlook can read it. RFC 5545 escaping and 75-octet folding; AI reasons go in DESCRIPTION. (VTIMEZONE: PR #8 review.)
- "Show me another option" on the Confirm card re-runs the same request excluding the rejected option by its **stable key** (lodging: provider + place + property; flight: the whole itinerary, i.e. airline + cabin + every leg's flight number and departure, so rejecting a round trip doesn't hide other returns or cabins with the same outbound), not its per-search id. A re-search with different dates, guests, or passengers can't bring it back. Excluded options are removed from search results before either agent sees them, so they can't be re-proposed or booked. Mock providers now keep property and flight identity stable per place / route and date, with prices varying by query, as real providers do. (PR #8 review.)
